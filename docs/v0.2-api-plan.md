# v0.2 API Plan

This document tracks the breaking API work planned for a future v0.2 release.
The v0 policy allows breaking changes in a minor release, but the current v0.1
line should continue to take compatible fixes and additive helpers.

## Goals

- Make `Condition` easier to copy, pass, and reuse without accidental shared
  mutable state.
- Add renderer-oriented APIs that can report what was consumed, what remains,
  and how wide the rendered output is.
- Keep the existing string-based helpers as the simple path for table cells,
  tree renderers, and status text.
- Validate breaking changes against known importers before tagging v0.2:
  `github.com/apstndb/spanner-mycli` and `github.com/apstndb/spannerplan`.

## Non-Goals

- Do not add prose/word-boundary wrapping, streaming APIs, or public token
  streams without a concrete importer requirement.
- Do not expose internal scanner tokens just because the implementation may use
  them internally.
- Do not change v0.1 behavior in place. Breaking changes belong behind a v0.2
  release plan and release notes.

## Release Decisions

### Condition Copy Semantics

Current APIs are pointer-oriented: `NewCondition` returns `*Condition`, and
methods use pointer receivers. v0.1 now has `Clone`, which gives callers an
explicit compatible copy path. v0.2 makes value-oriented use clearer by:

- documenting `Condition` as a small value configuration type;
- using value receivers for methods that only read options, so each operation
  uses a snapshot of the configuration; and
- preserving the pointer-returning `NewCondition` and `Clone` APIs, including
  the nil-safe `Clone` contract, because known importers store `*Condition` and
  a constructor return-type break would add churn without improving behavior.

Migration check:

- `spanner-mycli` uses `Condition` literals and package-level helpers.
- `spannerplan` uses `NewCondition()` with `TrimTrailingSpace = true`.

### Consumption-Reporting Cut API

Renderers often need to split a cell while knowing how much was displayed and
what remains. A v0.2 API can make this explicit instead of forcing callers to
infer it from `Truncate` output.

Candidate shape:

```go
type CutResult struct {
    Text      string
    LineBreak string
    Rest      string
    Width     int
    Overflow  bool
}

func (c Condition) Cut(s string, width int) CutResult
```

`spannerplan/treerender` now provides a concrete importer requirement. Its
hand-written `wrapChunks` helper repeatedly calls `Truncate` and advances the
raw input by the byte length of the rendered result. That assumption is unsafe:

- `Truncate` expands tabs even when the input fits, so rendered text can be
  longer than the source and cause a slice-bounds panic;
- smaller tab expansions can instead skip source bytes without a panic;
- the downstream fallback for an overwide grapheme consumes one rune and can
  split a multi-rune grapheme cluster; and
- its LF-only outer split disagrees with `Truncate` treating LF, CRLF, and CR as
  line breaks.

The core contract is that rendered byte length or display width must never be
used to advance raw source. `Rest` is always an exact byte suffix of the input,
while `Text` is render-ready and expands tabs from column zero. A natural LF,
CRLF, or CR is consumed into `LineBreak`, so every call with non-empty input
consumes at least one complete grapheme or one line break. This avoids empty-line
stalls and gives callers an explicit stop cause:

- `LineBreak != ""` means a natural line boundary was consumed;
- `Rest != "" && LineBreak == ""` means the width forced the cut; and
- `Rest == ""` means the input ended.

For positive widths, an overwide first grapheme is consumed whole and reported
through `Overflow`; grapheme clusters are never split. Widths less than or equal
to zero are unbounded because `Cut` has a wrapping lane, not a truncation cap.
`Cut` follows `Wrap` options, including safe scanner-based handling of
`ControlSequences8Bit`, and does not apply `TrimTrailingSpace`. Its fragments do
not inject SGR reset/replay sequences; callers inserting content between cuts
own the terminal state. `WrapLines` is the self-contained line-oriented surface.

An interim downstream fix may normalize tabs and defensively verify that
rendered chunks are source prefixes, but that relies on an undocumented
`Truncate` property and is a migration aid rather than a new API guarantee.

### Hanging-Indent Wrapping

Tree and table renderers often need a different first-line width from
continuation-line width. v0.2 can add a wrapping API that returns lines with
width metadata instead of only a joined string.

Candidate shape:

```go
type WrapLine struct {
    Text      string
    LineBreak string
    Width     int
    Overflow  bool
}

func (c Condition) WrapLines(s string, firstWidth int, restWidth int) []WrapLine
```

The same `spannerplan/treerender.wrapChunks` helper is direct demand for this
surface: it already implements separate first-line and continuation budgets,
trailing-space handling, and line assembly. `firstWidth` applies only to the
first output line; every later output line uses `restWidth`, whether the prior
break was natural or inserted. Non-positive lane widths are unbounded.

`LineBreak` preserves a natural LF, CRLF, or CR, while inserted hard wraps use
LF. `TrimTrailingSpace` remains a `Condition` option and applies to each
rendered line. SGR reset-before-break and replay-on-the-next-line follow `Wrap`,
including `ControlSequences8Bit`. N consumed line breaks produce N+1 results:
empty input returns one empty line, and a trailing natural break returns a
trailing empty line with an empty `LineBreak`.

A v0.2 acceptance case must be able to replace the downstream helper while
preserving tabs, grapheme clusters, all three supported natural line-break
forms, and byte-for-byte `Wrap` output when both lane widths are equal.

### Non-Positive Truncation Width

`Truncate(maxWidth <= 0)` currently returns `tail` as-is, which can exceed the
claimed cap. In v0.2, a non-positive truncation cap means nothing fits:
`Truncate` returns an empty string and `TruncateInfo` returns width zero while
reporting truncation exactly when the input was non-empty. This differs from
the unbounded non-positive lanes used by `Wrap`, `Cut`, and `WrapLines`; release
notes must call out the distinction and the breaking migration.

## Migration Checklist

Before tagging v0.2:

1. Create a branch that applies the candidate API changes.
2. Update local examples and package documentation.
3. Test `spanner-mycli` against the branch, especially table and streaming
   formatters that use `Condition`, `StringWidth`, `Truncate`, `FillLeft`, and
   `FillRight`.
4. Test `spannerplan` against the branch, especially `asciitable`, `plantree`,
   and `treerender` code paths that use `NewCondition()` with
   `TrimTrailingSpace = true`. Include downstream regressions for tab expansion
   that previously panicked or lost bytes, an overwide multi-rune grapheme, and
   LF/CRLF/CR input. Use those tests to validate explicit source-consumption and
   progress guarantees before freezing the result types.
5. Publish v0.2 release notes with the breaking changes, migration notes, and
   minimum Go version.

## Relationship to Open Backlog

- Issue #15 landed normalized SGR style state, which the v0.2 design can reuse
  if it chooses self-contained styled fragments.
- Issue #16 stays demand-driven. `spannerplan/treerender` now supplies concrete
  demand for consumption-reporting cuts and hanging-indent wrapping; prose
  wrapping, streaming APIs, and a public token surface still need their own
  importer requirements.
- Issue #20 landed internal scanner consolidation. The scanner can support the
  v0.2 APIs, but it should remain internal unless a public token surface is
  independently justified.
