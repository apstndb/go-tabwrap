# v0.2 API Plan

This document tracks the breaking API work planned for a future v0.2 release.
The v0 policy allows breaking changes in a minor release, but the current v0.1
line should continue to take compatible fixes and additive helpers.

## Goals

- Make `Condition` easier to copy, pass, and reuse without accidental shared
  mutable state.
- Add renderer-oriented APIs that can report what was consumed, what remains,
  and how wide the rendered output is.
- Keep the existing string-based helpers as the simple path for table cells,
  tree renderers, and status text.
- Validate breaking changes against known importers before tagging v0.2:
  `github.com/apstndb/spanner-mycli` and `github.com/apstndb/spannerplan`.

## Non-Goals

- Do not add prose/word-boundary wrapping, streaming APIs, or public token
  streams without a concrete importer requirement.
- Do not expose internal scanner tokens just because the implementation may use
  them internally.
- Do not change v0.1 behavior in place. Breaking changes belong behind a v0.2
  release plan and release notes.

## Candidate Changes

### Condition Copy Semantics

Current APIs are pointer-oriented: `NewCondition` returns `*Condition`, and
methods use pointer receivers. v0.1 now has `Clone`, which gives callers an
explicit compatible copy path. v0.2 can make value-oriented use clearer by:

- documenting `Condition` as a small value configuration type;
- considering value receivers for methods that only read options;
- preserving `NewCondition` as a convenience constructor if it still helps
  migration;
- keeping `Clone` as the recommended way to normalize defaults before mutation.

Migration check:

- `spanner-mycli` uses `Condition` literals and package-level helpers.
- `spannerplan` uses `NewCondition()` with `TrimTrailingSpace = true`.

### Consumption-Reporting Cut API

Renderers often need to split a cell while knowing how much was displayed and
what remains. A v0.2 API can make this explicit instead of forcing callers to
infer it from `Truncate` output.

Candidate shape:

```go
type CutResult struct {
	Text      string
	Rest      string
	Width     int
	Overflow  bool
	Truncated bool
}

func (c Condition) Cut(s string, width int) CutResult
```

Design questions:

- Whether `Rest` should retain original tabs/control sequences exactly.
- Whether `Text` and `Rest` are self-contained terminal fragments or raw source
  slices. Self-contained fragments would need explicit SGR reset/replay
  behavior, likely using the same normalized SGR state model as `Wrap`; raw
  slices would instead require callers to preserve surrounding terminal state.
- Whether `Cut` should operate on one logical line only or stop at the first
  LF/CRLF/CR line break.
- Whether `Truncated` and `Overflow` are both needed, or whether one flag is
  enough once `Rest` is available.

### Hanging-Indent Wrapping

Tree and table renderers often need a different first-line width from
continuation-line width. v0.2 can add a wrapping API that returns lines with
width metadata instead of only a joined string.

Candidate shape:

```go
type WrapLine struct {
	Text  string
	Width int
}

func (c Condition) WrapLines(s string, firstWidth int, restWidth int) []WrapLine
```

Design questions:

- Whether line-break bytes should be preserved in `Text` or represented
  separately.
- What `firstWidth <= 0` or `restWidth <= 0` means. Options include aligning
  with `Wrap(width <= 0)` by treating that lane as unbounded, returning no
  visible text for that lane while reporting overflow, or rejecting the shape
  through result metadata instead of string-only behavior.
- Whether trailing-space trimming remains a `Condition` option or a per-call
  option for line-oriented APIs.
- Whether SGR carry-over should be represented in each line exactly as `Wrap`
  emits it today.

### Non-Positive Truncation Width

`Truncate(maxWidth <= 0)` currently returns `tail` as-is. That behavior is
documented and should stay stable in v0.1. v0.2 can reconsider it only if the
new cut/truncation result API gives callers a clearer alternative.

Decision options:

- Keep the current behavior for compatibility with existing callers.
- Return an empty string and report overflow through metadata.
- Treat non-positive width as an error-like condition represented in the result
  type rather than through a string-only return.

## Migration Checklist

Before tagging v0.2:

1. Create a branch that applies the candidate API changes.
2. Update local examples and package documentation.
3. Test `spanner-mycli` against the branch, especially table and streaming
   formatters that use `Condition`, `StringWidth`, `Truncate`, `FillLeft`, and
   `FillRight`.
4. Test `spannerplan` against the branch, especially `asciitable`, `plantree`,
   and `treerender` code paths that use `NewCondition()` with
   `TrimTrailingSpace = true`.
5. Publish v0.2 release notes with the breaking changes, migration notes, and
   minimum Go version.

## Relationship to Open Backlog

- Issue #15 tracks normalized SGR style state and can land compatibly before
  v0.2.
- Issue #16 stays demand-driven. Do not add extra renderer APIs until a known
  importer needs them.
- Issue #20 tracks internal scanner consolidation. It can support the v0.2 APIs
  later, but it should remain internal unless a public token surface is justified.
